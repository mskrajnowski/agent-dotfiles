# Git workflow

Follow this workflow for every code change. The developer reviews and merges; the agent never does.

## 1. Branch first

- Create a topic branch before making any change — even trivial fixes.
- **Never commit to the default branch** (e.g. `main`, `master`).
- One goal per branch; a branch maps to one PR. If the task spans unrelated goals, use separate branches.

## 2. Branch naming

Loosely follow Conventional Commits prefixes, plus a short kebab-case slug:

```
feat/pdf-export
fix/login-timeout
chore/update-deps
refactor/split-parser
docs/rewrite-readme
```

Pick the prefix matching the change type; the slug summarizes the goal. No issue numbers or author initials unless the project's conventions say otherwise.

## 3. Commit per logical change

- One commit = one logical change. Split multi-part work into a series of commits rather than one dump.
- Stage only files relevant to the commit — check `git status`/`git diff` before staging. Never commit unrelated or leftover files.
- Do not mix formatting/reformatting with behavior changes — separate commits.
- Generated code and lockfiles are regenerated by tooling, not hand-edited; stage the regenerated result with the change that caused it.
- If the working tree contains uncommitted work you did not create, do not stage or commit it — flag it to the developer instead.

## 4. Commit messages

Use [Conventional Commits](references/CONVENTIONAL-COMMITS.md): `type(scope): summary`. The full spec is in that local reference — read it there instead of fetching it from the web.

- Brief and specific. `fix(auth): use refresh token before expiry`, not `update code`.
- Subject style: imperative mood ("add footer", not "added footer"), no trailing period, subject line roughly ≤ 72 characters.
- Body only when it adds real context (why, not what); no essays.
- Scope is optional; use it when it disambiguates.
- Reference issues in the PR description, not in commit footers — easier to edit, and the forge links them at the PR level. Exception: a `revert` commit may reference the reverted SHAs in its footer, per the spec.
- Breaking changes follow the spec: `!` after type/scope (`feat(api)!:`) or a `BREAKING CHANGE:` footer.

## 5. Open the PR early

- Open the PR as soon as the branch has its first meaningful commit, and push regularly. The developer can follow progress in the PR before review even starts.
- Keep the PR title and description current as work progresses:
    - **Title** describes the task — the goal, not the current state. Set it once when opening the PR; it should rarely need editing.
    - **Description** states the goal and the current state of the implementation. Update it after meaningful progress. A short checklist of what is done and what remains before the change is ready for final review keeps progress visible at a glance — tick items off as you go, remove them once everything is complete.
- Use the `forge-pr` skill's `update_pr.py` to refresh title and description.
- Commits stay atomic; the PR is the unit of completion — it carries the full set of commits needed to finish the task.
- Use the `forge-pr` skill for PRs on the forge (`forge.local`): `git push -u origin <branch>`, then open the PR there.
- The PR summary states what changed and how it was verified (tests run, checks). If something could not run, say so.
- Agents do not merge PRs or resolve review comments — the developer does. When asked to address review feedback, follow the `forge-pr` feedback loop: fix → commit locally → reply to each addressed comment with the short commit SHA → push (`--force-with-lease`). Reply before pushing, per `forge-pr`.

## 6. Keep PR history stable

- Once a PR is open, do not rewrite its pushed history. Review comments map to specific commits; rewriting breaks that traceability.
- Exception: when stuck, share your state with a `wip: ...` commit and push it. Once you and the developer have figured things out, amend or fixup those commits away — a `wip:` commit is scaffolding, not history.
- Cleaning up a messy history is welcome right before the developer merges. If the history is messy at review time, suggest a cleanup pass (squash fixup commits, interactive rebase) as part of the handoff.

## 7. Staying in sync with the target branch

- If the PR has no conflicts and does not need changes from the target branch, leave it as is — rebase before merging.
- If you need changes from the target branch (or conflicts exist), rebase onto it. Prefer linear history over merge commits.

## 8. Stacked branches

- When work builds on another open PR, branch from that PR's branch and open your PR against it instead of the default branch. Note the dependency in the PR description.

## 9. Safety

- Ask before irreversible actions: rewriting pushed history, force pushes (outside the `--force-with-lease` review loop), changing credentials, deleting data.
- Never commit secrets. Redact logs and keep real user data out of tests and fixtures.
